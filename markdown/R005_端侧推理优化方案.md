# 国讯芯微 R005 端侧推理优化方案

> **硬件**: R005NP+ (8核 Cortex-A78AE 2.0GHz + 157 TOPS INT8 NPU + 星速 NMA加速器)  
> **目标**: 从 llama.cpp CPU-only 推理 → NPU/GPU 加速推理，将 30~60 秒的动作规划缩短到 5~10 秒  
> **与 4090 的关键区别**: R005 没有 NVIDIA GPU，但有专用 NPU 和 ARM 加速器，优化路线完全不同

---

## 一、R005 硬件加速能力分析

### 1.1 R005NP+ 硬件参数（来自国讯芯微官方）

| 组件 | 规格 | 对推理的影响 |
|------|------|------------|
| **CPU** | 8核 Cortex-A78AE @ 2.0GHz | ARM v8.2，支持 NEON/SVE，llama.cpp CPU 后端可用 |
| **NPU** | **157 TOPS INT8** | 专用 AI 加速器，INT8 推理比 CPU 快 10~50 倍 |
| **星速 NMA 加速器** | 国讯芯微自研 | 多模态感知加速，可能支持 VLM 预处理 |
| **NIIC SYNC MANAGER** | 同步管理器 | 多传感器数据同步，降低推理延迟 |
| **GPU** | 集成 Mali-G52 MC3 | OpenCL 支持，llama.cpp 可作为 OpenCL 后端 |
| **内存** | 推测 4~8GB LPDDR | 限制模型大小，2B-3B INT8 可运行 |
| **NECRO 白泽系统** | 硬实时 OS | 微秒级调度，减少推理任务被抢占 |

### 1.2 关键结论

**R005 的推理加速有两条独立路线**：

## 三、方案 C + D：今天就能做的优化（零依赖）

### 3.1 llama.cpp NEON 极致编译参数

当前部署的编译参数已经是 NEON 优化版本，但还有进一步提升空间：

```bash
cd ~/ai-r005/llama.cpp
rm -rf build && mkdir build && cd build

# 极致 NEON 优化编译
cmake .. \
    -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_C_FLAGS="-O3 -march=armv8.2-a+fp16+dotprod -ffast-math -funroll-loops" \
    -DCMAKE_CXX_FLAGS="-O3 -march=armv8.2-a+fp16+dotprod -ffast-math -funroll-loops" \
    -DGGML_NATIVE=OFF \
    -DGGML_OPENMP=ON \
    -DGGML_CPU_ARM_ARCH=armv8.2-a \
    -DLLAMA_BUILD_SERVER=ON \
    -DGGML_AVX=OFF \
    -DGGML_AVX2=OFF \
    -DGGML_FMA=OFF \
    -DGGML_CUDA=OFF \
    -DGGML_VULKAN=OFF

make -j$(nproc)
```

**关键优化参数说明**：

| 参数 | 作用 | 预期提速 |
|------|------|---------|
| `-O3` | 最高级编译优化 | 5~10% |
| `-march=armv8.2-a+fp16+dotprod` | 启用 FP16 半精度 + 点积指令 | 10~20% |
| `-ffast-math` | 允许浮点运算重排序（精度轻微损失） | 5~10% |
| `-funroll-loops` | 循环展开减少分支 | 5~10% |
| `GGML_CPU_ARM_ARCH=armv8.2-a` | 针对 A78 核心优化 | 10~15% |

**合计预期提速**: 30~50%（1.3~1.5 倍）

### 3.2 量化模型选择（最直接的提速方法）

| 模型 | 量化 | 大小 | 内存 | 推理速度 | 精度损失 |
|------|------|------|------|---------|---------|
| Qwen3.5-2B | Q5_K_M | 1.5GB | 1.5GB | 基准 | 最小 |
| Qwen3.5-2B | **Q4_K_M** | **1.2GB** | **1.2GB** | **+20%** | 小 |
| Qwen3.5-2B | **Q3_K_M** | **0.95GB** | **1GB** | **+40%** | 中 |
| Qwen3.5-2B | **Q2_K** | **0.7GB** | **0.8GB** | **+60%** | 较大 |
| RoboBrain2.0-7B | Q4_K_M | 4.7GB | 4.7GB | 基准 | 小 |
| RoboBrain2.0-7B | Q3_K_M | 3.8GB | 3.8GB | +20% | 中 |

**操作**：直接下载更小的量化版本替换，无需重新编译。

```bash
# Qwen3.5-2B 换 Q3_K_M (提速 40%)
cd ~/ai-r005-qwen35/models
wget https://www.modelscope.cn/models/unsloth/Qwen3.5-2B-GGUF/repo?FilePath=Qwen3.5-2B.Q3_K_M.gguf
# 修改 start_server.sh 指向新模型
```

### 3.3 llama.cpp 运行时参数调优

```bash
# 启动参数优化
./llama-server \
    -m model.gguf \
    --ctx-size 2048 \        # ← 减小上下文窗口（默认4096太大）
    --threads 8 \             # ← 用满8核
    --batch-size 256 \       # ← 减小batch降低内存压力
    --ubatch-size 128 \      # ←  micro-batch 调小
    --flash-attn \           # ←  启用FlashAttention（如果编译支持）
    -ngl 0                   # ←  确认没有GPU层（R005无NVIDIA GPU）
```

**ctx-size 减半 → 内存减半 → KV-cache 更小 → 速度更快**

## 四、方案 B：llama.cpp + OpenCL（Mali-GPU）

R005 集成的 **Mali-G52 MC3 GPU** 支持 OpenCL 2.0，llama.cpp 可以用 OpenCL 后端加速矩阵运算。

### 4.1 编译 llama.cpp + OpenCL

```bash
cd ~/ai-r005/llama.cpp
rm -rf build && mkdir build && cd build

# 安装 OpenCL 依赖
sudo apt-get install -y ocl-icd-opencl-dev opencl-headers clinfo

# 编译时启用 OpenCL
cmake .. \
    -DCMAKE_BUILD_TYPE=Release \
    -DGGML_OPENCL=ON \           # ← 启用 OpenCL！
    -DGGML_OPENCL_EMBED_KERNELS=ON \
    -DGGML_NATIVE=OFF \
    -DGGML_OPENMP=ON \
    -DLLAMA_BUILD_SERVER=ON \
    -DGGML_CUDA=OFF

make -j$(nproc)
```

### 4.2 验证 OpenCL

```bash
# 查看 Mali-GPU 是否被识别
clinfo | grep -i mali

# 启动 llama-server，会自动使用 OpenCL
# 日志中应出现: "ggml_opencl: using platform ... Mali"
```

### 4.3 预期效果

| 指标 | CPU-only | +OpenCL (Mali-G52) | 提速 |
|------|---------|-------------------|------|
| Qwen3.5-2B Q4 | 10 t/s | 20~30 t/s | **2~3x** |
| RoboBrain Q4 | 3 t/s | 8~12 t/s | **2~3x** |

**限制**: Mali-G52 是入门级 GPU，只有 3 个计算单元，不能期望太高。

## 五、方案 A：NPU 加速（终极优化，需国讯芯微支持）

### 5.1 R005 NPU 概况

- **算力**: 157 TOPS INT8（理论峰值）
- **对比**: 比 CPU 推理快 10~50 倍
- **关键问题**: NPU 需要专用的模型格式和驱动 SDK

### 5.2 使用 NPU 的前提条件

需要确认以下信息（需联系国讯芯微技术支持）：

```
1. NPU 驱动是否已安装？
   → 检查: ls /dev/npu* 或 dmesg | grep -i npu

2. 是否有官方 SDK？
   → 类似 NVIDIA CUDA Toolkit 的 NPU 开发包
   → 可能包含: 模型转换工具、推理库、示例代码

3. 支持的模型格式？
   → 可能支持: ONNX、TFLite、NNAPI、或国讯芯微自研格式
   → llama.cpp 是否有该 NPU 的后端？

4. 支持的算子？
   → NPU 可能不支持 Transformer 的所有算子
   → 需要确认 attention、layer_norm 等是否支持
```

### 5.3 如果 NPU SDK 可用

**路径 1: llama.cpp 添加 NPU 后端**

```bash
# 假设国讯芯微提供了类似这样的编译选项
cmake .. \
    -DGGML_NPU=ON \           # ←  hypothetical NPU backend
    -DNPU_SDK_PATH=/opt/npu-sdk \
    ...
```

**路径 2: 使用国讯芯微官方推理框架**

```bash
# 假设官方提供了类似这样的工具
/opt/npu-sdk/bin/model-converter \
    --input model.gguf \
    --output model.npu \
    --quant int8

/opt/npu-sdk/bin/inference-server \
    --model model.npu \
    --port 8080
```

**路径 3: ONNX Runtime + NPU Execution Provider**

```bash
# 1. 将 GGUF 模型转换为 ONNX
python3 convert_gguf_to_onnx.py model.gguf model.onnx

# 2. 使用 ONNX Runtime + NPU EP
python3 -m onnxruntime.tools.convert_float_to_16 model.onnx

# 3. 推理
import onnxruntime as ort
session = ort.InferenceSession("model.onnx", 
    providers=["NPUExecutionProvider"])  # ← 使用 NPU
```

### 5.4 预期效果（如果 NPU 能用）

| 指标 | CPU-only | NPU (157 TOPS) | 提速 |
|------|---------|---------------|------|
| Qwen3.5-2B INT8 | 10 t/s | **100~200 t/s** | **10~20x** |
| 汉堡包规划 | 30 秒 | **2~3 秒** | **10~15x** |

## 八、与 4090 GPU 优化的对比

| 优化手段 | 4090 (NVIDIA GPU) | R005 (ARM + NPU) | 可行性 |
|---------|-------------------|------------------|--------|
| **CUDA** | ✅ `GGML_CUDA=ON` | ❌ 无 NVIDIA GPU | 不可用 |
| **TensorRT** | ✅ NVIDIA 官方 | ❌ 不支持 ARM | 不可用 |
| **FlashAttention** | ✅ 原生支持 | ⚠️ CPU版本较慢 | 部分可用 |
| **NEON/SVE** | ❌ x86 不支持 | ✅ `march=armv8.2-a` | 已启用 |
| **OpenCL (Mali)** | ❌ 无用 | ✅ `GGML_OPENCL=ON` | 可用 |
| **NPU 加速** | ❌ 无 NPU | ✅ 157 TOPS INT8 | **需 SDK** |
| **模型量化** | ✅ GGUF Q4/Q3 | ✅ GGUF Q4/Q3 | 通用 |
| **知识蒸馏** | ✅ 训小模型 | ✅ 训小模型 | 通用 |

**核心结论**: 4090 用 CUDA，R005 用 NPU + OpenCL。两条路线完全不同，但效果可以相当（都达到 10~20 倍提速）。
